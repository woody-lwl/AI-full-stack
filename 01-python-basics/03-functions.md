## 1. 场景引入

接口自动化项目刚开始时，你可能会在每个用例里直接写三类断言：状态码是否正确、响应体是否含有必填字段、响应耗时是否超限。两三个用例还不明显；当登录、下单、退款等几十个用例都复制这些判断后，问题就出现了：错误文案不统一，耗时阈值改一次要搜索很多文件，某些用例还可能漏掉一项检查。

重复代码真正危险的地方，不只是“行数多”，而是**同一条业务规则有了多份可能逐渐不一致的实现**。

**一句话直觉：函数把一段有明确输入、处理和输出的逻辑命名起来，让规则只实现一次，再从多个用例复用。**

本章把重复接口响应断言拆成三个小检查函数，再由一个组合函数聚合问题。重点不是追求函数数量，而是让每个函数只因一种检查规则变化而修改。

### 2.1 先看重构前为什么难维护

下面是常见的重复写法（用于观察问题，不放入最终工程）：

```python
# 登录接口
login_errors = []
if login_status != 200:
    login_errors.append("状态码错误")
if "data" not in login_body:
    login_errors.append("缺少 data")
if login_elapsed_ms > 500:
    login_errors.append("响应超时")

# 下单接口：同样的规则又复制一遍，还可能漏改文案或阈值
order_errors = []
if order_status != 201:
    order_errors.append("状态码不正确")
if "data" not in order_body:
    order_errors.append("没有 data")
if order_elapsed_ms > 500:
    order_errors.append("太慢")
```

这些变量名虽然不同，逻辑结构却相同。适合抽取的信号是：代码重复表达同一个业务概念，而且未来应该一起变化。

### 2.2 拆成职责单一的检查函数

`src/api_response_checker/checker.py`：

```python
"""把重复的接口响应断言拆成可组合的检查函数。"""

from collections.abc import Mapping

# 模块级常量属于全局作用域；tuple 不可变，适合作为默认参数。
DEFAULT_REQUIRED_FIELDS: tuple[str, ...] = ("data",)


def check_status_code(actual: int, expected: int = 200) -> list[str]:
    """检查状态码，返回零条或一条问题描述。"""
    if actual == expected:
        return []
    return [f"状态码不一致：期望 {expected}，实际 {actual}"]


def check_required_fields(
    body: Mapping[str, object],
    required_fields: tuple[str, ...] = DEFAULT_REQUIRED_FIELDS,
) -> list[str]:
    """返回响应体中每个缺失必填字段的问题描述。"""
    return [
        f"响应体缺少必填字段：{field}"
        for field in required_fields
        if field not in body
    ]


def check_elapsed_time(
    elapsed_ms: float,
    max_elapsed_ms: float = 500.0,
) -> list[str]:
    """检查响应耗时是否超过阈值。"""
    if elapsed_ms <= max_elapsed_ms:
        return []
    return [
        "响应耗时超限："
        f"阈值 {max_elapsed_ms:.1f} ms，实际 {elapsed_ms:.1f} ms"
    ]


def check_api_response(
    status_code: int,
    body: Mapping[str, object],
    elapsed_ms: float,
    *,
    expected_status: int = 200,
    required_fields: tuple[str, ...] = DEFAULT_REQUIRED_FIELDS,
    max_elapsed_ms: float = 500.0,
) -> list[str]:
    """组合各项检查，并返回本次响应的全部问题。"""
    # 局部变量：每次调用都会创建新列表，不会污染下一次检查。
    errors: list[str] = []
    errors.extend(check_status_code(status_code, expected_status))
    errors.extend(check_required_fields(body, required_fields))
    errors.extend(check_elapsed_time(elapsed_ms, max_elapsed_ms))
    return errors
```

三个小函数分别只负责一种规则，组合函数只负责安排调用顺序和汇总结果。所有公开函数都有参数和返回值的类型注解，对应 `Req 1.2`。

### 2.3 参数、返回值与作用域如何落在真实调用中

`src/api_response_checker/__main__.py` 的核心调用：

```python
# 前三个实参按位置传入，适合含义稳定且调用时容易辨认的核心数据。
login_errors = check_api_response(
    200,
    {"data": {"token": "demo-token"}},
    128.4,
)

# * 后面的策略参数必须按关键字传入，调用处能直接看懂含义。
order_errors = check_api_response(
    500,
    {"message": "server error"},
    820.0,
    expected_status=201,
    required_fields=("data", "request_id"),
    max_elapsed_ms=500.0,
)
```

这里同时使用了四种关键机制：

- **位置参数**：`200`、响应体、`128.4` 按函数定义顺序绑定；
- **关键字参数**：`expected_status=201` 明确表达这个值的用途；
- **默认参数**：登录检查省略策略参数，采用状态码 `200`、必填 `data`、耗时上限 `500.0`；
- **返回值**：函数不直接中断测试，而是返回 `list[str]`，调用者可以打印、断言或写入报告。

作用域方面，`DEFAULT_REQUIRED_FIELDS` 位于模块全局作用域，用于表达共享且稳定的默认规则；`errors` 位于函数局部作用域，每次调用都会重新创建。函数返回后，调用者拿到的是该次调用的结果，不会与下一条用例共享错误列表。

## 3. 设计思考

### 3.1 为什么抽函数，而不是继续复制？

抽函数带来三个直接收益：规则有唯一实现位置；函数名比一串 `if` 更能表达意图；每条规则可以独立测试。判断是否值得抽取，不能只看“是否出现两次”，还应看它是否代表一个稳定概念、是否会独立变化、是否能说清输入与输出。

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 用例内直接断言 | 就地阅读简单，少量代码最快 | 重复后易产生规则漂移 | 一次性且只有一两行的专属判断 |
| 抽成检查函数 | 规则集中、可复用、易单测 | 需要设计参数和返回协议 | 多个用例共享同一检查规则 |
| 做成通用断言框架 | 可配置、扩展能力强 | 抽象成本高，初学阶段易过度设计 | 规则很多、多人长期维护的平台 |

本章选择检查函数，因为问题已经重复，但规模还不需要框架。

### 3.2 参数应该传什么？

参数是函数与外部世界的边界。`check_status_code(actual, expected)` 只接收完成状态码判断所需的数据，而不是接收整个 HTTP 客户端对象。边界越小，函数越容易理解、复用和测试。

组合函数的前三个参数是每次响应都不同的事实数据，因此允许位置传入；策略参数放在 `*` 后，强制调用者使用关键字。这样 `max_elapsed_ms=500.0` 比孤立的第四、第五、第六个数字更不容易传错。

默认值只用于团队中稳定、常见的规则。若不同接口几乎都有不同必填字段，就不应依赖默认值掩盖差异。`required_fields` 使用不可变 `tuple`，避免可变默认列表在多次调用之间共享修改。

### 3.3 为什么返回错误列表，而不是在函数里直接 assert？

返回 `list[str]` 让函数只负责“计算有哪些问题”，而把处理方式交给调用者：pytest 可以统一断言，命令行工具可以打印，报告模块可以保存。这种输入相同、返回结果相同、且不修改外部状态的检查函数接近**纯函数**，测试成本低。

直接 `assert` 的优点是用例短、失败立即；缺点是通常遇到第一个问题就停止，不利于一次看到完整响应质量。直接打印则有明显副作用，调用者难以复用结果。本章把打印留在 `__main__.py`，让核心检查逻辑与输出方式解耦。

### 3.4 返回一个错误，还是聚合全部错误？

聚合能让测试人员一次看到状态码、结构和性能问题，减少“修一个再跑一次”的往返；立即停止更适合后续检查依赖前置条件的场景。例如响应体根本不是可读取的映射时，继续检查字段可能没有意义。

本例的三个检查彼此独立，因此全部执行并按固定顺序聚合。返回协议统一为 `list[str]`，组合时只需 `extend`，不用分别处理 `None`、字符串和列表。

### 3.5 何时不要过度拆分？

函数不是越小越好。如果把一条直观表达式拆成 `is_equal()`、`build_message()`、`make_list()` 三层，读者需要不断跳转，反而更难理解。以下情况通常不急着抽：只出现一次、没有独立业务含义、抽取后参数比函数体还长，或者函数名只是重复代码字面意思。

合理边界是“一个函数只承担一个可描述、可测试的职责”，而不是“一个函数只能有一行”。本章中的 `check_api_response` 虽然调用了三项检查，但它的单一职责是**编排并聚合响应检查**，没有再次实现具体规则。

## 4. 常见坑

| 坑 | 后果 | 根本原因 |
|---|---|---|
| 使用 `def check(fields=[])` | 多次调用可能共享同一个列表，结果互相污染 | 默认参数在函数定义时求值，可变对象被复用 |
| 函数内部既检查、又打印、又写文件 | 难以单测，也无法自由选择错误处理方式 | 核心计算与副作用没有分离 |
| 传入整个客户端或测试上下文 | 函数依赖过多，难以在其他项目复用 | 没有缩小参数边界 |
| 六七个参数全部按位置传入 | 调用处看不出含义，顺序相近时容易传错 | 没有区分核心数据与配置策略 |
| 有的检查返回 `None`，有的返回字符串或列表 | 聚合代码充满类型判断 | 没有统一返回协议 |
| 为了“职责单一”把每行都拆成函数 | 跳转过多，命名困难，阅读成本上升 | 把代码行数误当作职责数量 |
| 在函数内修改全局错误列表 | 测试顺序影响结果，并行执行更危险 | 局部状态泄漏到全局作用域 |
| 捕获所有情况后只返回 `False` | 失败时不知道期望值、实际值和字段 | 返回值没有携带可定位信息 |

## 5. 最佳实践

1. **先找变化原因，再划分函数**：状态码规则、字段规则和耗时规则可能独立变化，因此分别封装；聚合顺序属于组合函数。
2. **参数只传完成职责所需数据**：优先传状态码、响应体和耗时，不让核心逻辑依赖网络客户端。
3. **公开函数补全类型注解**：类型标出输入边界和返回协议，方便 IDE、测试和代码 review；类型注解不替代运行时业务校验。
4. **策略参数优先用关键字**：当多个数字或配置含义相近时，用 `*` 强制关键字调用，降低传错顺序的风险。
5. **默认参数使用不可变值**：字符串、数字、`tuple` 通常安全；需要新列表时在函数体内创建。
6. **核心计算返回数据，边缘层处理副作用**：检查函数返回问题，入口负责打印，未来也能接入 pytest 或报告系统。
7. **统一小函数的返回协议**：本例都返回 `list[str]`，通过为空或非空表达检查结果，组合逻辑保持简单。
8. **给边界和组合行为写测试**：既测单个规则，也测阈值相等、多个错误顺序和重复调用不串数据。

这些实践适用于测试脚本、数据校验和小型工具。若以后检查项需要动态注册、分组和配置，再考虑策略对象或插件机制；不要在当前规模提前引入复杂框架。

## 6. 练习题

### 练习 1：抽取重复断言（基础）

**对应验收：模块①·函数；Req 1.2**

找一段你工作中至少重复两次的接口断言代码，先用一句话分别写出每段逻辑的职责，再完成重构：

- 抽出“检查响应头 `Content-Type`”函数；
- 参数至少包含实际值和期望值，公开函数带类型注解；
- 返回 `list[str]`，不要在核心函数中直接打印；
- 补充“匹配”和“不匹配”两个 pytest 用例。

验收标准：调用者不需要知道函数内部判断细节；另一位同事只看函数名、签名和测试，就能说明输入、输出与失败信息。

### 练习 2：组合退款接口检查（进阶）

**对应验收：模块①·函数；Req 1.2**

为退款接口新增金额检查：响应体中的 `refund_amount` 必须等于期望金额。请先设计函数签名，再实现并接入 `check_api_response` 的相邻练习副本。

要求：

- 不修改本章原始工程，复制到自己的练习目录；
- 金额检查函数只负责金额规则，不打印、不写文件；
- 覆盖金额正确、字段缺失、金额不一致；
- 构造一个同时包含状态码错误、金额错误和超时的响应，验证所有问题均被聚合；
- 解释为什么期望金额适合做参数，而不应该写成全局变量。

提示：先决定字段缺失由现有必填字段函数报告，还是由金额函数报告；两种方案都可行，但应避免同一个缺失问题被报告两次。

## 7. 小结与自检

- 函数把有明确输入、处理和输出的逻辑命名起来，核心价值是让业务规则只有一份实现。
- 位置参数适合少量、稳定、容易辨认的核心数据；关键字参数适合配置策略和含义相近的值。
- 返回数据比直接打印更容易组合与测试；副作用应尽量放在入口等边缘层。
- 全局常量表达共享规则，局部变量保存单次调用状态；不可变默认参数能避免跨调用污染。
- 职责单一按“变化原因”判断，不按函数行数判断；抽取应降低而不是增加理解成本。
- 本章示例的所有公开函数均带类型注解，并通过独立函数与组合入口实证 `Req 1.2`。
